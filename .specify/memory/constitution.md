# TV News with TanStack 憲章

## コア原則

### I. 型安全性ファースト

**全てのコードはTypeScriptのstrictモードを有効にして使用しなければならない。** 以下に対して型定義が必須：
- 全ての関数シグネチャ（パラメータと戻り値の型）
- 全てのコンポーネントprops
- 全てのAPIコントラクト（リクエスト/レスポンス）
- 全てのデータモデルとエンティティ
- 状態管理構造

**根拠**: 型安全性は実行時ではなくコンパイル時にエラーを検出し、IDEサポートを向上させ、生きたドキュメントとして機能し、自信を持ったリファクタリングを可能にする。リアルタイムデータを扱うニュースアプリケーションでは、型安全性がデータ破損とUIの不整合を防ぐ。

### II. パフォーマンス最適化

**パフォーマンスは最優先事項でなければならない。** アプリケーションは以下を活用すること：
- **TanStack Query**: 最適化されたデータフェッチ、キャッシング、同期のため
- **SSR（サーバーサイドレンダリング）**: TanStack Start経由で初期ページロードを高速化
- **コード分割**: 適切な箇所でコンポーネントとルートを遅延ロード
- **仮想スクロール**: 長いリスト（ニュースフィード、記事リスト）のため
- **メモ化**: React.memo、useMemo、useCallbackを戦略的に使用

**パフォーマンス目標**:
- 初期ページロード: 3G接続で2秒未満
- Time to Interactive (TTI): 3秒未満
- スムーズなスクロール: ナビゲーションとリストスクロール中に60fpsを維持

**根拠**: ニュース読者はコンテンツへの即座のアクセスを期待する。パフォーマンスが悪いと直帰率が高くなり、ユーザー体験が低下する。TanStack StartのSSRとQueryのインテリジェントなキャッシングは、高速でレスポンシブなアプリケーションの基盤を提供する。

### III. テストファースト開発（絶対必須）

**TDD（テスト駆動開発）は必須である。** ワークフローは以下に従うこと：

1. **最初にテストを書く** - テストを通じて期待される動作を定義
2. **ユーザーの承認を得る** - テストシナリオが要件と一致することを確認
3. **テストが失敗することを確認** - テストが正しい理由で失敗することを確保
4. **コードを実装** - テストが通る最小限のコードを書く
5. **テストが通ることを確認** - 実装が要件を満たすことを確認
6. **リファクタリング** - テストをグリーンに保ちながらコードを改善

**テストカバレッジ要件**:
- **ユニットテスト** (Vitest): 全てのサービス、ユーティリティ、ビジネスロジック
- **コンポーネントテスト** (React Testing Library): ユーザーインタラクションを持つ全てのUIコンポーネント
- **統合テスト** (Vitest + MSW): API統合ポイント、データフェッチフロー
- **E2Eテスト** (Playwright): 重要なユーザージャーニー（記事を読む、ニュース検索、カテゴリナビゲーション）

**根拠**: TDDは実装開始前に要件がテスト可能であることを保証し、リグレッションバグを防ぎ、実行可能なドキュメントとして機能し、自信を持ったリファクタリングを可能にする。ニュースアプリケーションには信頼性が必要であり、ユーザーはコンテンツが正確で一貫して表示されることを信頼している。

### IV. シンプルさとYAGNI

**今必要なものだけを実装すること。** 以下を避ける：
- 早すぎる抽象化と過剰設計
- "将来の柔軟性のための"機能や設定
- 不要な間接層
- 推測による汎用化

**適用すべきこと**:
- **YAGNI (You Aren't Gonna Need It)**: 仮説的な将来の要件のために構築しない
- **KISS (Keep It Simple)**: 機能する最もシンプルなソリューションを選択
- **継承より合成**: Reactの合成パターンを優先
- **直接的なソリューション**: 3行の似たコードは、早すぎる抽象化より良い

**根拠**: シンプルなコードは理解、テスト、保守、リファクタリングが容易である。過剰に設計されたソリューションは認知負荷を増やし、変更を困難にする。シンプルに始める—重複が問題になった時にのみパターンに向けてリファクタリングする。

### V. CI/CD自動化

**自動テストとデプロイメントは必須である。** 全ての変更は以下を満たすこと：
- 自動テストをトリガーする（ユニット、統合、E2E）
- マージ前に全ての品質ゲートを通過
- mainへのマージ時にステージングへ自動デプロイ
- ワンクリックでの本番デプロイメントをサポート

**必須の自動化**:
- **Pre-commitフック**: リンティング、フォーマット、型チェック
- **CIパイプライン**: 全てのPRで全テストを実行
- **ビルド検証**: 本番ビルドが成功することを確保
- **デプロイメントパイプライン**: ステージングへの自動デプロイメント

**根拠**: 手動テストとデプロイメントはエラーが発生しやすく遅い。自動化は一貫した品質を保証し、デプロイメントの摩擦を減らし、迅速な反復を可能にし、統合問題を早期に捕捉する。

## 技術スタック

**このセクションは、原則に沿った承認済み技術選択を定義する。**

### コアフレームワーク
- **TanStack Start (React)**: SSR、ストリーミング、ルーティング、サーバー関数を提供するフルスタックフレームワーク
- **TypeScript**: 最大限の型安全性のためstrictモードを有効化
- **Vite**: ビルドツールと開発サーバー（TanStack Startに統合）

### 状態とデータ管理
- **TanStack Router**: 型安全なルーティング（TanStack Startに統合）
- **TanStack Query**: サーバー状態管理、キャッシング、同期
- **React Context**（必要時）: 最小限のクライアントサイド状態用

### テストスタック
- **Vitest**: 高速なユニット・統合テスト
- **React Testing Library**: ユーザー中心のクエリによるコンポーネントテスト
- **Playwright**: 重要なユーザージャーニーのE2Eテスト
- **MSW (Mock Service Worker)**: テスト用のAPIモック

### コード品質
- **ESLint**: JavaScript/TypeScriptのリンティング
- **Prettier**: コードフォーマット
- **TypeScript Compiler**: 型チェック

### オプションライブラリ（追加時に正当化が必要）
- 全ての新規ライブラリはシンプルさ原則に対して正当化されなければならない
- パフォーマンス原則に対するバンドルサイズの影響を考慮
- TypeScriptサポートを持つライブラリを優先（型安全性原則）

## 開発ワークフロー

**このセクションは必須の開発実践を定義する。**

### 機能開発
1. **仕様**: ユーザーストーリーを含む機能仕様を作成（spec-template.md参照）
2. **計画**: 実装計画を作成（plan-template.md参照）
3. **憲章チェック**: 計画が全ての原則に沿っているか検証
4. **タスク**: 依存関係順にタスクに分解（tasks-template.md参照）
5. **実装**: テストファースト開発に従う（原則III）
6. **レビュー**: 全てのコードはマージ前にレビューが必要

### コードレビュー要件
- TypeScript strictモード準拠を検証
- パフォーマンス考慮事項を確認（不要な再レンダリング、大きなバンドル）
- テストが存在しTDDワークフローに従うことを確認
- シンプルさを評価—不要な複雑さにフラグを立てる
- CI/CDが通過することを検証

### テスト戦略
- **テストの独立性**: 各ユーザーストーリーは独立してテスト可能でなければならない
- **テストカバレッジ**: 80%以上を目指すが、クリティカルパスを優先
- **テストパフォーマンス**: ユニットテスト < 100ms、統合テスト < 1秒/テスト
- **外部サービスのモック**: テストでのAPI呼び出しにはMSWを使用

### ブランチとデプロイメント
- **機能ブランチ**: `###-feature-name` 形式
- **mainブランチ**: 常にデプロイ可能、保護されている
- **ステージング**: mainへのマージ時に自動デプロイ
- **本番**: ステージング検証後に手動承認

## ガバナンス

**憲章はこのプロジェクトの開発実践における最高権威である。**

### 修正プロセス
1. **提案**: 変更提案を根拠とともに文書化
2. **影響分析**: 既存コードとテンプレートへの影響を評価
3. **チーム承認**: 合意が必要（またはプロジェクトオーナーの承認）
4. **バージョン更新**: セマンティックバージョニングに従う（下記参照）
5. **テンプレート同期**: 全ての依存テンプレートとドキュメントを更新
6. **移行計画**: 破壊的変更の場合、既存コードの移行パスを文書化

### バージョニングポリシー
- **MAJOR** (X.0.0): 後方互換性のない変更（原則の削除/再定義、主要なスタック変更）
- **MINOR** (0.X.0): 新しい原則の追加または既存原則の実質的な拡張
- **PATCH** (0.0.X): 明確化、表現の改善、非意味的な洗練

### コンプライアンスとレビュー
- **全てのPRはこの憲章への準拠を検証しなければならない**
- **実装計画で憲章チェックが必須**（plan-template.md）
- **シンプルさ原則に違反する場合、複雑さを正当化しなければならない**
- **定期監査**: 原則とコードベースの整合性を四半期ごとにレビュー

### テンプレートとの関係
- この憲章は `.specify/templates/` の使用方法を管理する
- テンプレート（spec、plan、tasks、commands）はこれらの原則に沿わなければならない
- テンプレートと憲章が矛盾する場合、憲章が優先される
- テンプレート更新は憲章準拠を維持しなければならない
